# PhiloMate 现有成果全面评审与优化建议

> 评审日期：2026-09-02  
> 评审对象：技术方案 PPT、阶段 3 测试报告、功能介绍图、线上演示网页  
> 评审视角：专业内容、产品体验、技术实现  
> 报告性质：现状审计与改进方案，不包含对原 PPT、Word 或网页代码的直接修改

## 1. 执行摘要

PhiloMate 的核心产品方向是成立的：它不是一般意义上的“哲学知识问答”，而是试图通过角色立场、哲学原典、语气控制、关系成长和可持续互动，把哲学思想转化为用户愿意长期接触的对话体验。现有成果已经具备较完整的产品雏形，也积累了语料处理、安全机制和内部 A/B 测试等技术材料。

当前主要问题不在于“没有内容”，而在于内容、产品和证据尚未被组织成一条统一、可信、可验证的技术叙事：

1. **技术报告的主线不够集中。** PPT 中同时存在产品逻辑、算法模块、比赛模板字段和内部修改备注，信息很多，但评委不容易快速理解“用户遇到什么问题—产品如何解决—技术为什么有效—证据是什么”。
2. **文档存在明显不一致和未完成痕迹。** 哲学家数量、阶段 3 测试状态、处理流程的阶段划分前后不统一；尾页仍保留占位文字和内部提示；测试报告在跨平台渲染时出现中文字体缺失风险。
3. **线上网页视觉完成度较好，但首屏资源过重。** 实测一次进入角色页面累计传输约 **36.42 MB**，其中图片约 **18.86 MB**、字体约 **11.23 MB**、JSON 约 **2.88 MB**、视频约 **3.29 MB**。一个中文字体文件约 **11.77 MB**，单张角色图约 **2.83–4.77 MB**，且部分资源重复请求。
4. **“素材消失”最可能首先来自本地存储模型，而不仅是网络。** 当前书籍、封面等数据主要写入浏览器 `localStorage`；封面被压缩后以 Base64 字符串写入 JSON。该方案容量小、同步阻塞主线程、写入异常未充分处理，并且数据受域名、协议、浏览器和隐私模式影响，容易出现保存失败、状态丢失或换入口后“像是消失”的现象。
5. **书籍自动录入适合先做 ISBN MVP。** 短期可通过“ISBN/条形码 → 后端聚合 Google Books 与 Open Library → 用户确认候选结果”的方式，自动补全大部分基础字段；中文版本信息不足时，再接入有授权的图书馆联合编目或商业数据。豆瓣当前不适合作为未授权生产数据源，更不建议抓取。
6. **现有测试可以作为内部探索性证据，不能承担强结论。** 当前 A/B 结果为 A 34、B 27、平局 3；报告自身也谨慎指出不应宣称“显著更好”。样本量、随机化、重复生成、评审者构成、置信区间和外部用户测试仍需加强。

建议先执行以下五项 P0 工作：

- 统一 PPT 中的产品定义、哲学家数量、流程和测试结论，删除所有占位与内部备注。
- 修复字体、图片、JSON、视频的体积与缓存策略，将冷启动关键资源从 30 MB 级降至 2–3 MB 级。
- 修复遮罩层拦截导航、加载失败导致整组数据不可用、保存异常无提示等稳定性问题。
- 将书籍封面和记录迁移到 IndexedDB；为保存、迁移、备份和存储容量建立可见状态。
- 增加 ISBN 搜索补全的最小可用版本，同时开始构建正式测试集和可复现评测流程。

## 4. 技术报告专业性评审

### 4.1 当前材料的优点

- 产品不是简单地给模型添加“你是某哲学家”的系统提示，而是尝试建立语料、态度、语气、关系和安全等多层控制，具备可讲述的技术差异。
- 报告能够正面讨论“AI 味”“假语录”“缺少分寸”等真实失败类型，比只展示成功案例更可信。
- 阶段 3 测试已经采用 A/B、盲评和部分换序，说明团队具备证据意识。
- 技术材料包括数据来源、典型案例、边界和修订记录，后续不需要推倒重写，重点是重新组织和收敛。

### 4.2 PPT 的主要问题与修改建议

#### 4.2.1 产品口径不一致

PPT 多处写“5 位哲学家”，包括马克思；但当前线上产品实际只有孔子、苏格拉底、王阳明、福柯 4 位。如果第五位尚未可用，应统一写成“当前上线 4 位，规划扩展至 5 位”，否则评委现场打开演示时会立即发现不一致。

阶段 3 测试也存在相互冲突：一页写“已完成”，后面的旧页面又写“阶段 3 待做”，尾页仍保留待补素材和网盘链接提示。这些内容会降低报告可信度，应删除旧状态页，而不是同时保留。

#### 4.2.2 技术流程缺少唯一版本

PPT 中至少出现三种不同粒度的流程表达：案例页的详细步骤、六阶段流程图、架构页的简化链路，同时又使用 `mood`、分寸 A/B/C/D、态度 0–5、`path1/path2` 等术语。建议建立唯一的“标准处理链路”，其他页面只引用其中的局部模块。

推荐统一为：

```text
用户输入
  → 风险与意图识别
  → 对话状态构建（角色、关系、情绪、上下文）
  → 哲学证据检索（原典、传记、主题标签）
  → 回应策略规划（立场、语气、追问或收束）
  → 大模型生成
  → 引用与安全校验
  → 输出、关系更新与可观测记录
```

每个阶段应明确四件事：输入、输出、规则或模型、失败时的降级方式。若实际系统尚未实现某一步，则应标注“规划中”，不要把设计目标写成已经上线的能力。

#### 4.2.3 叙事仍偏比赛模板，而不是产品逻辑

目前大量页面在回答“我们用了什么”，但对“用户为什么持续回来”和“技术怎样支撑这个循环”讲得不够。建议把主要叙事改成：

1. 用户问题：通用 AI 的哲学家角色容易迎合、编造和失去立场。
2. 产品价值：不是工具型问答，而是具有立场、边界和关系变化的“哲学同桌”。
3. 用户旅程：选角色 → 发起对话 → 收到有依据的回应 → 收藏/窗台 → 主动事件 → 再次对话。
4. 技术机制：角色状态、证据检索、生成策略和校验如何协作。
5. 效果证据：代表案例、盲测结果、失败类型和改进前后对比。
6. 边界与路线图：当前能做什么、暂时不能做什么、下一步怎样验证。

#### 4.2.4 页面信息密度与版式问题

- 多个三栏页面文字密度过高，适合做内部技术文档，不适合比赛现场快速阅读。
- 数据来源页右侧长字符串出现明显溢出/裁切，应改为短名称、版本号与脚注链接。
- 页脚保留“V0 草稿”“请直接在 PPT 里改”等内部说明，必须删除。
- 尾页包含“贴主页五人同桌画面”“贴一轮完整对话”“10 分钟以内”等占位提示，不能出现在提交版。
- 目前页码显示方式容易让人误解总页数；建议统一按提交版实际页数重新编号。

#### 4.2.5 数据来源与版权说明不足

“公开传记”“经典语录”等描述过于宽泛。建议为每类语料记录：来源名称、版本、出版或公开地址、授权状态、采集日期、可用范围、清洗规则和语料版本号。尤其要区分：

- 原文直接引用；
- 现代译文或二次转述；
- 模型基于材料生成的第一人称表达。

第三类不能被展示成哲学家的真实原话。对外界面可以使用“思想依据”或“相关原典”标记，并提供出处展开层。

### 4.3 建议的 PPT 主体结构

建议将比赛主体控制在 12–15 页，登记材料或完整测试案例放入附录：

1. 标题与一句话价值主张。
2. 用户问题：普通角色扮演为何不够。
3. 目标用户、场景与明确边界。
4. 一张端到端产品旅程图。
5. 产品差异：有立场、有依据、有关系变化。
6. 唯一版本的处理链路。
7. 系统架构与客户端/服务端边界。
8. 语料构建、溯源和版权治理。
9. 安全、拒答与失败降级。
10. 2–4 个代表案例，分别对应关键指标。
11. 评测设计。
12. 结果、置信边界和失败分析。
13. 性能与稳定性改进数据。
14. 产品路线图与总结。
15. 团队资质、演示地址和可用二维码。

登记表中包含姓名、生日、电话、地址等个人信息。正式报送给主办方可保留必要版本，但评审预览版、演示版、公开 PDF 和网盘分享版必须脱敏。

### 4.4 Word 测试报告的主要问题与修改建议

#### 4.4.1 跨平台字体兼容属于提交阻断项

测试报告大量使用“微软雅黑”，并存在异常的东亚语言字体配置。在本次跨平台渲染中，绝大部分中文未正常显示，只剩英文、数字和标点。这意味着评委若使用不同操作系统、Office 版本或在线预览器，可能看到近乎空白的报告。

建议：

- 统一使用可嵌入、跨平台的中文字体，例如思源黑体/思源宋体或 Noto CJK；若比赛要求使用系统字体，则至少在导出 PDF 前检查字体替换结果。
- 使用 Word 样式管理标题、正文、表格和代码，不要依靠大量直接格式。
- 提交前分别在 Windows Office、WPS、LibreOffice/在线预览和最终 PDF 中检查。
- 最终 PDF 应确认字体已嵌入，并逐页检查中文、表格、分页和页码。

#### 4.4.2 测试结论需要保持克制

当前结果是 A 34、B 27、平局 3；去掉平局后约为 56:44。按哲学家分组后的表现差异较大：孔子和王阳明偏向产品方案，苏格拉底和福柯没有形成同样优势。现有报告已经正确提醒“不宜宣称显著更好”，提交版应继续使用以下表述：

> 内部探索性盲测显示，产品方案在部分角色和场景中呈现出积极趋势，但当前样本不足以证明总体显著优于基础模型；结果主要用于定位失败类型和指导下一轮设计。

不建议使用“效果得到验证”“全面优于大模型”等强结论。

#### 4.4.3 修订后重跑尚未构成正式复测

报告展示了修订后的重新生成结果，但没有对这些结果进行新的盲评、随机换序和量化评分。因此，它可以证明“团队完成了针对性修订”，不能证明“问题已经被修复”。建议将这一部分命名为“修订样例与待复测假设”，并用全新留出题重新盲评。

#### 4.4.4 报告结构建议

正式测试报告可重构为：

1. 测试目标与预先假设。
2. 被测系统、模型、提示词、语料和代码版本。
3. 测试集构造、覆盖矩阵与留出规则。
4. 生成参数、重复次数、随机化与盲法。
5. 评分量表、评审者构成与验收阈值。
6. 主要结果、置信区间和统计方法。
7. 失败分类及代表案例。
8. 修订、回归与独立复测。
9. 性能、稳定性与安全指标。
10. 局限性与下一步计划。
11. 附录：完整题目、输出、评分和原始记录。

## 5. 网页产品与交互体验评审

### 5.1 已有体验优势

- 首页视觉风格统一，角色形象有识别度，移动端能够自适应为卡片布局。
- 对话、窗台、纸团、主动事件、好感度与礼物共同构成了比单次聊天更完整的产品循环。
- “不只顺从用户”的角色定位和功能图中表现出的关系机制，有机会形成长期留存差异。

### 5.2 主要产品体验问题

| 问题现状 | 原因分析 | 改进方案 | 实现难度 | 优先级 |
|---|---|---|---|---|
| 自动出现的纸团/事件遮罩会拦截“窗台”等导航点击，实测造成超过 5 秒无法点击 | 遮罩层覆盖全屏并接收指针事件，关闭方式不够明确 | 遮罩外层非必要区域设置 `pointer-events: none`；卡片保留事件；增加明确关闭按钮、自动消退和“不再自动弹出”；导航操作优先 | 低 | P0 |
| 移动端聊天输入提示文字换成两行，角色图占据较大空间 | 组件尺寸和文案没有针对小屏单独设计 | 移动端缩短 placeholder；降低角色图最大高度；保证输入区和关键操作始终在安全区内 | 低 | P1 |
| 浅色图标位于明亮背景时对比度不足 | 视觉设计优先于可读性，缺少统一的对比度检查 | 为顶部按钮增加半透明底板、描边或阴影；按 WCAG 对比度和触控尺寸检查 | 低 | P1 |
| 1200×1200 桌面窗口首页上下空白较多 | 首页布局以固定中心区域为主，没有充分利用宽屏和方屏 | 使用响应式高度、背景层和内容层；在不增加认知负担的前提下展示一句价值说明或最近互动入口 | 低 | P2 |
| 加书表单完全依赖人工填写，且字段不足 | 尚未接入书籍数据源，数据模型偏向当前界面而非标准书目 | 增加 ISBN、完整出版日期、版本、译者、简介、来源；支持扫描、搜索补全和候选确认 | 中 | P0/P1 |
| 植物选择在添加后不可修改 | 将装饰绑定视作不可逆业务字段，增加了用户犯错成本 | 保存前提供预览，保存后允许修改；若确有产品机制，应说明原因并提供有限更换机会 | 低 | P1 |
| 无明显的保存状态、失败提示、同步/本地标识 | 数据层错误没有被转换成用户可理解状态 | 显示“正在保存/已保存/保存失败/仅保存在本机”；提供重试、导出和恢复入口 | 中 | P0 |
| 同一本书可能重复录入不同记录 | 缺少标准标识和去重策略 | ISBN-13 为主键候选；无 ISBN 时使用标题、作者、出版社和版本的相似度提示重复 | 中 | P1 |

### 5.3 建议补充的专业用户能力

从长期使用场景看，建议逐步补充：

- 对话中的“思想依据”展开：显示原典、章节、译本或“模型转述”标记。
- 对可能是原话的句子提供“核验出处”入口，避免用户误当作真实引语。
- 收藏内容可回到具体对话上下文，而不是只有孤立卡片。
- 书籍与对话联动：某本书的阅读进度、相关对话和哲学主题形成一条学习轨迹。
- 用户可导出自己的书架、笔记和对话摘要，降低对单一浏览器的依赖。
- 对低落、危机、自伤等场景提供明确、审慎的安全提示和人工帮助入口。
- 对主动消息提供频率控制、关闭开关和触发说明，避免“有生命感”变成打扰。

## 6. 网页卡顿：实测结果与原因分析

### 6.1 本次现场测得的关键数据

在一次桌面端冷启动并进入孔子对话页的过程中，浏览器记录到：

| 资源类别 | 传输量（约） |
|---|---:|
| 图片 | 18.86 MB |
| 中文字体 | 11.23 MB |
| JSON | 2.88 MB |
| 视频 | 3.29 MB |
| 总计 | 36.42 MB |

其中：

- 单个中文字体文件约 11.77 MB，加载耗时约 13 秒。
- 四张角色图单张约 2.83–4.77 MB。
- `corpus_annotated.json` 约 2.91 MB。
- 教室背景视频约 3.45 MB。
- HTML 的 `DOMContentLoaded` 约 0.32 秒，但完整 `load` 约 13.63 秒，说明主要瓶颈不是 HTML 解析，而是大体积静态资源。
- 已部署静态响应未观察到有效的 `Cache-Control`、ETag/Last-Modified 或内容压缩响应头；部分角色资源存在重复请求。

这些数据足以解释弱网和移动端的明显卡顿，也会放大切换角色、重载页面和网络波动时的素材闪烁。

### 6.2 卡顿原因分层

#### 前端渲染与主线程

- 大图解码、Base64 封面转换、Canvas 压缩和同步写入 `localStorage` 都会占用主线程。
- 如果历史对话、书籍卡片和角色状态每次都整体重新渲染，数据增加后会产生长任务和掉帧。
- 2.9 MB JSON 的下载、解析、筛选如果在主线程一次完成，也会阻塞交互。

#### 资源加载

- 首页预加载所有角色的大图，但用户一次只会进入一个角色。
- 角色页再次请求相同资源，缓存策略不足导致重复传输。
- 字体、图片和视频均没有按真实显示尺寸与首屏优先级优化。
- 多个角色数据文件使用一次性并行加载；单个请求失败可能使整组角色数据加载失败。

#### 网络与服务端

- 当前演示使用裸 IP 和 HTTP，缺少 HTTPS、HTTP/2/3、CDN 等现代分发能力。
- 静态资源无长期缓存和压缩，使每次重载都付出较高成本。
- 若后端接口没有请求超时、重试、请求去重和慢查询监控，网络波动会直接暴露为界面等待。

#### 数据处理与持久化

- `localStorage` 是同步 API，保存大 JSON 时会阻塞主线程。
- Base64 会比原始二进制额外增加约三分之一体积。
- 多本带封面的书籍容易触及浏览器存储配额。
- 一次保存整个集合会随书籍数量增长而变慢，也提高局部失败造成整体异常的风险。

### 6.3 性能问题整改表

| 问题现状 | 原因分析 | 改进方案 | 实现难度 | 优先级 |
|---|---|---|---|---|
| 冷启动累计传输约 36.42 MB | 字体、角色图、视频、全量语料同时或过早加载 | 首屏只加载必要角色缩略图和界面资源；进入角色后再加载该角色数据；设置性能预算 | 中 | P0 |

| 列表随数据增加而变卡 | 可能整体重渲染和 DOM 数量增长 | 组件粒度拆分、缓存计算、虚拟列表、增量更新；以 Performance trace 验证 | 中 | P1 |
| 图片压缩和大 JSON 解析阻塞主线程 | 计算密集任务在 UI 线程执行 | 图片压缩、OCR、较大数据解析迁移到 Web Worker；展示进度和取消入口 | 中 | P1 |
| 不清楚真实用户性能 | 缺少前端性能采集与阈值 | 接入 Web Vitals、长任务、资源错误率和页面级埋点；按设备/网络分组 | 中 | P1 |

建议建立以下性能验收目标：

- 移动 4G 冷启动 LCP 小于 2.5 秒。
- INP 小于 200 ms，CLS 小于 0.1。
- 首屏关键传输量不高于 2–3 MB。
- 已缓存角色之间切换小于 1 秒。
- 静态资源缓存命中后不重复下载大图、字体和语料。

## 7. 素材消失、重新加载和状态丢失

### 7.1 已确认的高风险机制

当前网页将书架等业务数据写入 `localStorage`，书籍封面经过 Canvas 压缩后以 Data URL/Base64 写入同一份 JSON。这一实现有以下风险：

1. **配额不足。** 浏览器通常只提供有限的源站存储空间，多个封面很容易超限。
2. **异常未处理。** `localStorage.setItem` 可能抛出 `QuotaExceededError`、安全策略异常或序列化异常；若没有 `try/catch`，保存流程会被中断。
3. **同步阻塞。** 写入大字符串会阻塞主线程，表现为点击后卡住。
4. **源站隔离。** `http://IP`、未来的 `https://域名`、不同端口是不同存储空间；迁移地址后，原数据仍在旧源站，看起来像“全部消失”。
5. **浏览器隔离。** 更换浏览器、用户配置、设备、隐私模式或清理站点数据后，本地记录不会自动存在。
6. **整包覆盖。** 如果多个组件基于旧快照写回整个集合，后写入可能覆盖先写入，产生丢记录。

### 7.2 其他可能原因

- 组件的 `key` 或路由切换导致组件卸载重建，内存状态未持久化。
- 请求失败时把已有素材状态清空，而不是保留旧数据并显示重试。
- 多个资源通过 `Promise.all` 加载，任意一个失败导致整体拒绝。
- 图片使用临时 Blob URL 后过早执行 `URL.revokeObjectURL`。
- 服务器资源 URL 过期，或新部署覆盖旧文件路径。
- 并发接口返回顺序不同，旧请求晚到后覆盖新状态。
- Service Worker、浏览器缓存和服务端版本不一致。
- 后端保存成功但读取接口使用不同用户、角色或版本键。

### 7.3 快速定位方法

建议为“素材消失”建立一条完整事件时间线，而不是只看最后的页面状态：

```text
用户操作
  → 前端状态变更
  → 持久化开始
  → 持久化成功/失败
  → 组件重新渲染或路由切换
  → 素材请求开始/结束
  → 最终可见状态
```

#### 浏览器开发者工具

- **Network**：启用 Preserve log，分别测试冷缓存、热缓存、Slow 4G、Offline；观察重复请求、失败状态、取消请求、响应时间、传输体积和缓存命中。
- **Performance**：记录点击、加书、切角色和返回窗台；查找超过 50 ms 的 Long Task、图片解码、布局重排和 GC。
- **Application**：检查 `localStorage`、IndexedDB、Cache Storage、Service Worker；在保存前后比较记录数量和体积。
- **Memory**：多次切换角色后抓取 Heap Snapshot，确认图片和组件是否持续滞留。
- **Console**：捕获 `QuotaExceededError`、JSON 解析异常、资源 404/CORS 和未处理 Promise。

#### 前端日志

至少记录：

- `session_id`、匿名 `user_id`、页面、角色、应用版本和数据 schema 版本；
- 操作名称、对象 ID、前后版本、写入字节数、存储剩余量；
- 请求 ID、URL 类型、状态码、耗时、重试次数和是否命中缓存；
- `window.onerror`、`unhandledrejection` 和资源加载错误；
- 保存失败的异常类型，但不要上传用户的完整对话、书籍封面或敏感文本。

#### 后端与接口监控

- 每个请求生成 `request_id`，前后端日志一致。
- 记录 API 的 P50/P95/P99、错误率、超时率和重试率。
- 区分 DNS/连接/TTFB/下载/解析/渲染耗时。
- 若有对象存储，监控签名 URL 过期、404、403、跨域和 CDN 回源。
- 可使用 Sentry 等错误平台和 OpenTelemetry 链路，但必须配置敏感信息脱敏。

### 7.4 稳定性整改表

| 问题现状 | 原因分析 | 改进方案 | 实现难度 | 优先级 |
|---|---|---|---|---|
| 封面和书架存在消失风险 | Base64 封面与整包 JSON 存在 `localStorage` | 将结构化记录和二进制封面迁移至 IndexedDB；每本书独立记录，事务写入 | 中 | P0 |
| 保存失败时用户不知道 | 存储异常未转成可见状态 | 所有写入统一 `try/catch`；显示失败原因、重试和导出备份；失败时不清空现有 UI | 低 | P0 |
| 单个资源失败可能使整组角色数据不可用 | 使用全有或全无的并行加载 | 使用 `Promise.allSettled` 或资源级 fallback；关键与非关键资源分级；局部失败不阻断对话 | 低至中 | P0 |
| 切换页面后素材重新加载/闪烁 | 未缓存、组件卸载时清空、无占位 | 保留最近一次成功数据；稳定缓存键；骨架屏只用于首次加载；失败时显示旧内容+重试 | 中 | P0 |
| 地址从 IP/HTTP 切换到域名/HTTPS 后数据“消失” | 浏览器源站隔离 | 上线前提供一次性导出/导入或迁移机制；尽早固定正式域名和 HTTPS | 中 | P0 |
| 多页面/多操作可能互相覆盖 | 整个集合读改写，无版本控制 | 记录级更新、版本号/时间戳、乐观锁；监听 `storage`/BroadcastChannel 或统一状态仓库 | 中 | P1 |
| 浏览器存储被清理后无法恢复 | 无账号同步或备份 | 短期支持 JSON 导出/导入；中期接入用户账号、服务端数据库和对象存储 | 中至高 | P1/P2 |
| 网络失败触发空状态 | 请求层缺少超时、去重和过期数据策略 | `AbortController`、超时、指数退避、请求去重、stale-while-revalidate | 中 | P1 |
| 数据结构升级可能导致旧记录不可读 | 无 schema 版本和迁移 | 在数据中写 `schemaVersion`；提供幂等迁移、备份和失败回滚 | 中 | P1 |

建议的持久化分层：

```text
内存状态：当前页面交互
IndexedDB：书籍元数据、封面 Blob、对话索引、离线队列
Cache Storage：可重新下载的版本化静态资源
服务端数据库：账号、跨设备同步、关系与记录的权威状态
对象存储/CDN：封面和用户上传图片
```

如果比赛阶段暂时不建设账号系统，最低限度也应做到 IndexedDB、容量检测、保存错误提示、导出/导入和正式域名固定。

## 8. 书籍信息自动录入方案

### 8.1 目标体验

推荐把现有“完整手工表单”改成“一处输入、多级补全”：

1. 用户扫描书背 EAN-13 条形码，或输入 ISBN/书名。
2. 系统校验 ISBN，并在服务端并行查询多个数据源。
3. 若只有唯一高可信结果，自动填入表单；若存在多个版本，展示封面、出版社、年份和装帧供选择。
4. 对冲突字段显示来源和置信度，由用户确认。
5. 用户只补充未找到的字段，再选择植物并保存。
6. 保存时进行 ISBN 和相似书名去重。

需要注意：**ISBN 通常标识具体版本或载体，而不仅是抽象作品。** 同一本作品的精装、平装、不同译本、再版和电子版可能有不同 ISBN，因此候选页必须展示版本信息，不能只按书名自动覆盖。

### 8.2 数据源可行性

#### Google Books API

Google Books 官方 Volumes API 支持通过 `isbn:`、标题等方式检索，典型字段包括书名、作者、出版社、出版日期、ISBN、页数、简介和封面。它适合作为国际书籍和公开原型的第一数据源，但中文图书的具体版本覆盖不稳定，不能承诺每本都命中。

使用时应通过后端代理统一控制请求、缓存和合并，并按 Google 的品牌、归属和服务条款展示必要来源信息。不要默认把第三方返回内容永久复制为自建数据库，缓存和再分发规则需要按字段与使用方式核对。

#### Open Library

Open Library 提供 Search API 和 Covers API，可按 ISBN 查找记录和封面，适合作为免费补充源。其官方开发者说明明确强调公共利益和人本发现用途，不建议把在线 API 当成高流量第三方产品的完整数据后端；批量用途应考虑其数据 dump，并遵守许可和原始数据权利边界。

因此它适合作为 MVP 的补充与兜底，不应成为唯一生产依赖。

#### 豆瓣

当前未发现可作为新项目稳定接入依据的官方公开图书 API 文档。豆瓣现行法律声明明确限制未经书面许可使用其内容、图书条目信息、评分评论以及通过爬虫或衍生应用利用相关数据。

结论：

- 不建议使用未公开、历史遗留或逆向得到的接口。
- 不建议抓取网页或盗链封面。
- 如果确实需要豆瓣数据，应联系豆瓣取得书面商务授权，并确认字段、缓存、展示、调用量和终止后的数据处理方式。
- 即使某个旧接口当前仍可访问，也不能据此视为合法、稳定的生产能力。

#### 中国国家图书馆联合编目中心（OLCC）

OLCC 提供面向成员机构的 Z39.50 书目下载、ISBN 批量查询等服务，官方页面也列出了服务方式和部分计费规则。它对中文版本信息更有价值，但通常需要机构成员身份、成员代码或业务联系，不是匿名公共 API。

若项目有高校或图书馆合作方，建议通过学校图书馆确认是否已有联合编目服务资格；否则直接与服务中心沟通授权和费用。接入前应做实际中文书样本的命中率、字段完整率和使用权测试。

#### OCLC WorldCat

WorldCat Search API 可按 ISBN/OCLC 标识查找书目，适合图书馆或商业合作场景。官方说明显示，生产访问通常与 OCLC 订阅或商业合作相关。它可作为中长期机构级数据源，不适合默认假设为免费公开接口。

#### ISBN 机构数据

国际 ISBN 机构的 Global Register 主要是出版者注册信息，不是一个免费、完整、面向终端产品的全球书籍元数据库。ISBN 本身只是标识符，不能自动提供封面、页数和简介。国家 ISBN 机构或商业服务可能提供元数据，但需分别核实授权、覆盖和费用。

### 8.3 推荐的多数据源合并架构

```text
扫码/ISBN/书名/OCR
        ↓
输入标准化与 ISBN 校验
        ↓
服务端查询编排器
  ├─ Google Books 适配器
  ├─ Open Library 适配器
  ├─ OLCC/图书馆适配器（获授权后）
  └─ 商业书目数据适配器（按需）
        ↓
字段标准化 + 候选聚类 + 版本识别
        ↓
逐字段评分与合并
        ↓
用户确认冲突/低置信字段
        ↓
保存规范记录、字段来源和抓取时间
```

建议的统一数据结构：

```json
{
  "isbn13": "",
  "isbn10": "",
  "title": "",
  "subtitle": "",
  "authors": [],
  "translators": [],
  "publisher": "",
  "publishedDate": "",
  "edition": "",
  "pageCount": null,
  "language": "",
  "description": "",
  "coverCandidates": [],
  "sourceRecords": [],
  "fieldProvenance": {},
  "confidence": 0,
  "fetchedAt": ""
}
```

合并规则应按字段执行，而不是选择一条记录覆盖全部字段：

- ISBN 完全匹配的具体版本优先于书名模糊匹配。
- 出版社、出版日期、版次和页数优先采用精确 ISBN 的图书馆或授权书目记录。
- 封面只使用与该 ISBN/版本一致、尺寸与许可允许的候选。
- 简介往往带有数据源版权，应单独记录来源和展示规则。
- 多源冲突时不静默覆盖，向用户展示“出版社/年份/页数”的差异。
- 每个字段保留来源、原值、获取时间和置信度，便于纠错与刷新。

### 8.4 ISBN 扫码

纸质书背面的商品条码通常为 EAN-13，可在网页端使用 ZXing 的浏览器实现调用摄像头，也可在原生移动端使用 Google ML Kit 等离线条码识别组件。识别后还必须：

- 去除空格和连接符；
- 校验 EAN-13/ISBN-13 校验位；
- 判断是否为 978/979 ISBN 前缀；
- 转换和保存规范 ISBN-13；
- 处理条码无法识别、多个条码和非图书商品码。

当前演示站使用 HTTP。浏览器摄像头 `getUserMedia` 通常要求安全上下文，因此在上线网页扫码前必须迁移到正式域名和 HTTPS；否则部分浏览器会直接拒绝摄像头权限。

### 8.5 OCR 识别封面、书脊和版权页

OCR 建议作为 ISBN 无法扫描或无条码时的辅助入口，而不是最终数据源：

1. 用户拍摄封面、书脊或版权页。
2. OCR 提取候选书名、作者、出版社、ISBN/CIP 字符串。
3. 对候选文本进行纠错、ISBN 校验和字段识别。
4. 再查询书目数据源，并让用户选择版本。

可选方案包括：

- **PaddleOCR**：开源、中文能力较强，适合服务端或本地部署；需要自行做模型部署、图像预处理和性能优化。
- **腾讯云通用 OCR 等云服务**：接入快，支持旋转和坐标结果；需要评估费用、隐私、上传授权和网络依赖。
- **浏览器端 OCR**：隐私较好但模型下载和移动设备性能压力较大，不宜与当前已经偏重的首屏资源一起加载。

书脊文字可能竖排、反光、弯曲且背景复杂，成功率通常低于正面封面和版权页。产品上应引导用户优先扫条码，其次拍版权页，再尝试书脊。

### 8.6 书籍录入实施表

| 问题现状 | 原因分析 | 改进方案 | 实现难度 | 优先级 |
|---|---|---|---|---|
| 书名、作者、出版社、页数等全部手填 | 无统一书目检索入口 | 增加 ISBN/书名输入与“搜索补全”；通过后端查询 Google Books + Open Library | 中 | P0 |
| 无法扫码 | 无条码识别和 HTTPS | 固定域名并启用 HTTPS；接入 ZXing EAN-13；校验 ISBN | 中 | P0/P1 |
| 单一数据源可能缺字段或版本错误 | 不同来源覆盖范围不同 | 建立适配器、规范模型、逐字段溯源合并和候选确认 | 中至高 | P1 |
| 中文图书版本命中不足 | 免费国际数据源对中国版次覆盖有限 | 与学校图书馆确认 OLCC/Z39.50 资格，或采购合规商业书目数据 | 高/含商务 | P1/P2 |
| 同名书/不同译本容易误选 | 只按标题，不识别版次 | 候选页展示封面、译者、出版社、日期、版次、ISBN；不得静默合并 | 中 | P1 |
| 封面来源可能失效或不可再分发 | 直接使用第三方远程 URL | 记录来源与许可；遵守缓存条款；必要时让用户上传自有封面或使用获授权对象存储 | 中 | P1 |
| 无条码或条码损坏时仍需手填 | 缺少辅助识别 | 增加版权页/封面 OCR，提取候选后再查 API | 中至高 | P2 |
| 批量录入效率仍低 | 一次只能录入一本且无队列 | 批量扫描队列、连续相机模式、去重和待确认列表 | 高 | P2 |

## 9. 正式测试方案建议

### 9.1 当前测试的主要局限

- 仅 4 位内部评审者和 16 个题目，样本不足。
- 每个哲学家×场景单元只有一个问题，难以区分题目偶然性与系统能力。
- 只生成一次，未控制大模型随机性。
- 换序不完全平衡，仍可能存在顺序偏差。
- 未记录完整生成参数、提示词版本、语料快照、代码版本和测试时间。
- 没有评审者一致性指标、置信区间或预先定义的验收阈值。
- “感觉有依据”与“真实出处正确”是不同指标，目前未充分分开。
- 修订样例使用相同或相近题目，存在针对测试集调优的风险。
- 缺少延迟、失败率、成本、截断率和外部用户体验数据。

### 9.2 下一轮测试设计

建议构建 80–120 题的固定测试集，覆盖：

- 4 位哲学家；
- 日常困惑、理论问答、低落情绪、用户纠错、价值冲突、安全边界；
- 简单、复杂、含混、诱导编造和多轮上下文；
- 至少 30% 的严格留出题，调参人员不能提前使用。

评测安排：

- 每个条件固定生成参数并独立生成 3 次，避免单次随机结果决定结论。
- A/B 顺序按评审者和题目平衡随机化，隐藏系统身份和样式线索。
- 8–12 名评审者，混合哲学专业学生/教师与目标用户，记录背景但匿名分析。
- 评分维度分离：角色一致性、事实/出处正确性、问题相关性、情绪分寸、对话意愿、安全、完整性。
- 出处正确性由具备专业能力的评审者核验，不用一般用户“看起来有依据”替代。
- 报告成对胜率、Wilson 置信区间，并按数据结构选择 McNemar 检验或配对 Bootstrap。
- 报告 Fleiss' κ 或 Krippendorff's α 等评审一致性指标。
- 预先写出合格阈值，例如安全通过率 100%、编造引语率低于某阈值、总体偏好下界超过基线。

### 9.3 同时记录系统指标

| 类型 | 建议指标 |
|---|---|
| 质量 | 角色一致性、来源正确性、相关性、情绪分寸、对话持续意愿 |
| 安全 | 危机场景合规率、侮辱/诱导应对、编造真实引语率 |
| 稳定 | 生成失败率、超时率、截断率、结构解析失败率 |
| 性能 | 首字延迟、总响应时间 P50/P95、页面 LCP/INP、资源失败率 |
| 成本 | 单轮输入/输出 Token、检索成本、模型调用成本 |
| 产品 | 完成首轮对话率、次日/7 日回访、收藏率、主动事件关闭率 |

## 10. 分阶段实施路线图

### 10.1 短期：3–5 个工作日（P0 快速修复）

#### 报告

- 统一 4/5 位哲学家口径、测试状态和标准流程。
- 删除 PPT 所有占位、内部备注、旧状态页面和公开版个人信息。
- 修复数据来源页溢出，压缩正文密度。
- 修复 Word 中文字体兼容，导出并逐页检查 PDF。
- 将测试结论改为“内部探索性结果”，不宣称显著提升。

#### 网页

- 修复纸团遮罩拦截导航。
- 压缩角色图、字体和视频；首屏只加载必要资源。
- 配置 Brotli/Gzip、版本化文件名和浏览器缓存。
- 所有本地保存增加异常捕获、失败提示和数据不清空保护。
- 资源加载从全有或全无改为局部降级，增加重试入口。
- 固定正式域名并上 HTTPS，为摄像头扫码和数据迁移做准备。

#### 书籍录入 MVP

- 表单增加 ISBN 字段和“搜索补全”。
- 后端并行查询 Google Books 与 Open Library。
- 展示候选版本，填入书名、作者、出版社、日期、ISBN、页数、简介和封面。
- 保存来源与抓取时间，进行 ISBN 去重。

### 10.2 中期：1–2 周（P1 功能和稳定性建设）

- 将书籍记录和封面从 `localStorage` 迁移到 IndexedDB，提供导出/导入。
- 建立数据 schema 版本、迁移、事务和记录级更新。
- 完成多数据源适配器、字段合并、置信度和来源展示。
- 加入 ZXing 条码扫描、ISBN 校验和连续录入体验。
- 建立前端错误、Web Vitals、请求链路与存储容量监控。
- 拆分语料包或改为服务端检索，降低客户端 JSON 体积。
- 建立正式评测集、盲评工具和原始结果数据结构。

### 10.3 中长期：2–6 周（P2 架构调整）

- 接入账号、服务端权威存储、对象存储和跨设备同步。
- 与学校图书馆/OLCC 或商业书目供应商完成授权和覆盖率验证。
- 增加封面、书脊、版权页 OCR 与批量扫描队列。
- 建立语料来源治理、版本发布、回滚和自动回归测试。
- 在真实目标用户中开展可用性测试和长期留存验证。
- 部署 CDN、HTTPS、完整可观测链路和性能告警。

## 12. 建议验收清单

### 提交材料

- [ ] 公开版中无电话、地址、生日等个人信息。
- [ ] 4/5 位哲学家、阶段 3 状态、模型名称和版本在全稿一致。
- [ ] PPT 无“草稿”“待贴图”“请修改”等内部文字。
- [ ] 每项已上线能力都有截图、演示或测试证据；规划能力明确标注。
- [ ] Word/PDF 在至少三种查看环境中文正常，无裁切和缺页。
- [ ] 测试结论包含样本量、限制和适当的统计表达。

### 网页性能与稳定性

- [ ] 移动 4G 冷启动关键传输量不高于 2–3 MB。
- [ ] 字体不再加载 10 MB 级完整 TTF。
- [ ] 角色大图不会在同一流程重复传输。
- [ ] 单个语料或图片失败不会清空整个页面。
- [ ] 遮罩、弹窗和主动事件不拦截主要导航。
- [ ] 存储配额不足时能明确提示并保留未丢失数据。
- [ ] 地址迁移前提供本地数据迁移或导出方案。
- [ ] 线上使用正式域名和 HTTPS。

### 书籍录入

- [ ] 输入或扫描有效 ISBN 后能展示候选版本。
- [ ] 错误 ISBN 有校验提示，不发起无效查询。
- [ ] 自动填充字段可编辑，冲突字段显示来源。
- [ ] 无结果、超时和限流都有可恢复的交互。
- [ ] 同 ISBN 不重复创建；不同版本不会被误合并。
- [ ] 数据源归属、缓存、封面展示和商业使用符合各自条款。

### 测试

- [ ] 测试集、提示词、模型、参数、语料和代码均有版本号。
- [ ] A/B 顺序平衡随机，评审者看不到系统身份。
- [ ] 每个条件有重复生成，保留原始输出和评分。
- [ ] 有留出测试集，修订后不在原题上自证成功。
- [ ] 同时报告质量、安全、性能、稳定和成本。

## 14. 最终结论

PhiloMate 当前最值得投入的不是继续堆叠更多角色或页面，而是先把“一个完整、可靠、可证明的产品循环”打磨出来：用户能够快速进入一位哲学家的对话，持续获得有立场且有依据的回应，把阅读和对话沉淀到不会丢失的窗台与书架中，并能用 ISBN 在几秒内完成一本书的录入。

比赛材料应围绕这条循环重写：用一条统一技术链路解释产品，用来源治理和安全边界建立专业性，用正式评测证明效果趋势，用性能和数据稳定性证明系统不是只在演示环境中可用。短期 P0 工作完成后，报告可信度、现场演示稳定性和产品完成感都会有明显提升；账号同步、机构书目数据和 OCR 批量录入则适合作为中长期架构建设。
